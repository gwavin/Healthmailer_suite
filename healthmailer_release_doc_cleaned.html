HealthMailer / printRxer Suite Release and Deployment Notes

This document is intended for enterprise deployment teams, third-party installers, and governance reviewers preparing a controlled HealthMailer / printRxer Suite deployment.

Release Bundle

Obtain the approved release bundle supplied for this release. For normal installation, extract the bundle and run the suite installer from the extracted folder. 

.\PrintRxerSuiteInstaller.exe

Target machines do not need the .NET SDK, Windows Driver Kit, Visual Studio, or C++ build tools.

SHA-256 Checksums

Verify release ZIPs against the SHA256SUMS.txt supplied in the release bundle.

Deployment Roles

  • printRxer printing machine: the workstation where users print prescriptions to the local printRxer printer queue.
  • HealthMailer sending machine: the machine signed into the approved Outlook/Healthmail sender mailbox.
  • Same-machine pilot: a pilot configuration where both roles use the same local handoff folder.

printRxer is installed once per workstation. Its watcher task is configured to start at logon for interactive Windows users, with a limited run level and parallel instances, so shared workstations do not depend on the IT/admin account that performed installation. The installer also starts the watcher for the current session; future sessions start at logon.

The same handoff folder must be configured for both components. For two-machine deployments, use a UNC path rather than a mapped drive. Access should be restricted to the required printing, sending, and support identities.

Network Share Permissions

Configure the shared handoff directory (e.g. \\server\HealthMailerDrop$\incoming) with the following access controls:

Identity NTFS / Directory Rights Share Permissions Purpose
Standard Users (Clinicians) Create/write package folders and files; avoid broad delete/modify rights over other users' packages where the file server supports this. Constrained Change / write access Allows local printRxer instances to upload generated PDFs and JSON metadata without giving ordinary users unnecessary control over other packages.
HealthMailer Process Account Read, Write, Modify, Delete Full Control Allows central HealthMailer watcher to poll, lock, read, and delete/archive files.

Recipient List Updates

printRxer reads the preferred recipient list from the configured handoff folder. The active runtime file must be placed here: 

<handoff folder>\recipients\recipients.csv

A third-party master file may be supplied using the current naming convention, for example: 

\\approved-server\approved-share\HM-Recipients_Master.csv

To update recipients, copy the supplied master CSV into the handoff recipient folder as a temporary file, then rename it to recipients.csv. This avoids clients reading a half-written file.

Recipient List Format Schema

The master CSV must follow the exact structure below (no patient-identifiable data should be included): 

RecipientName,RecipientEmail,Code
"Dr. Jane Doe","jane.doe@healthmail.ie","D123"
"NMH Outpatients Clinic","outpatients@nmh.ie","NMH-01"
$handoffRoot = "\\server\HealthMailerDrop$\incoming"
$source = "\\approved-server\approved-share\HM-Recipients_Master.csv"
$recipientFolder = Join-Path $handoffRoot "recipients"
$temporaryFile = Join-Path $recipientFolder "recipients.csv.tmp"
$activeFile = Join-Path $recipientFolder "recipients.csv"

New-Item -ItemType Directory -Force -Path $recipientFolder
Copy-Item -LiteralPath $source -Destination $temporaryFile -Force
Move-Item -LiteralPath $temporaryFile -Destination $activeFile -Force

printRxer refreshes the central recipient list on startup, periodically while the application is running, and when the user or support clicks Refresh recipients in the picker. Updates are not intended to be immediate on every workstation, especially if a machine has been asleep or printRxer has not restarted. The normal printRxer user should only need read access to the handoff recipient folder. The recipients CSV is an address book/configuration file only and must not contain patient names, MRNs, prescription details, or other patient-identifiable information. Support bundles and ProgramData evidence may contain patient-identifiable package/audit metadata and must remain on HSE-controlled machines or approved HSE support/governance channels.

HealthMailer user context: HealthMailer must be installed and run under the intended Outlook/Healthmail sender Windows user. Do not deploy it only as a generic system-context installation unless that exact arrangement has been validated, because Outlook COM automation depends on the signed-in user profile.
printRxer administrator approval: printRxer installation may require administrator approval because printer capture includes the port monitor, XPS driver, and local printRxer printer queue.

Three-Phase Deployment

Run commands from the extracted suite ZIP root. Use Start-Process -Wait -PassThru so GUI executables complete and return an exit code. Stop deployment on any non-zero exit code.

Phase 1: Pre-flight

$p = Start-Process -FilePath .\PrintRxerSuiteInstaller.exe -ArgumentList "--smoke-test" -Wait -PassThru
$p.ExitCode

Phase 2: Provision

$handoffRoot = "\\server\HealthMailerDrop$\incoming"

$p = Start-Process -FilePath .\payload\setup\printRxerSetup.exe -ArgumentList @(
  "--quiet",
  "--handoff-root",
  $handoffRoot
) -Wait -PassThru
$p.ExitCode
# First validation / dry-run deployment
$p = Start-Process -FilePath .\payload\setup\HealthMailerSetup.exe -ArgumentList @(
  "--quiet",
  "--handoff-root",
  $handoffRoot,
  "--send-mail",
  "false"
) -Wait -PassThru
$p.ExitCode

# Live sending deployment, after approval
$p = Start-Process -FilePath .\payload\setup\HealthMailerSetup.exe -ArgumentList @(
  "--quiet",
  "--handoff-root",
  $handoffRoot,
  "--send-mail",
  "true",
  "--sent-prescription-retention-days",
  "14"
) -Wait -PassThru
$p.ExitCode

First test runs should use SendMail=false unless Outlook sending has already been approved for the test mailbox. Enable live sending only after the sending mailbox, user profile, and governance checks are approved.

HealthMailer rejects recipient addresses outside the approved domain allow-list unless explicitly configured otherwise. The default allowed domains are healthmail.ie, hse.ie, nmh.ie, and rotunda.ie.

Same-machine pilot:

$handoffRoot = "C:\ProgramData\printRxer\handoff"

$p = Start-Process -FilePath .\payload\setup\printRxerSetup.exe -ArgumentList @(
  "--quiet",
  "--handoff-root",
  $handoffRoot
) -Wait -PassThru
$p.ExitCode

$p = Start-Process -FilePath .\payload\setup\HealthMailerSetup.exe -ArgumentList @(
  "--quiet",
  "--handoff-root",
  $handoffRoot,
  "--send-mail",
  "false"
) -Wait -PassThru
$p.ExitCode

Phase 3: Validate

$p = Start-Process -FilePath .\payload\setup\printRxerSetup.exe -ArgumentList "--validate" -Wait -PassThru
$p.ExitCode

$p = Start-Process -FilePath .\payload\setup\HealthMailerSetup.exe -ArgumentList "--validate" -Wait -PassThru
$p.ExitCode

The suite smoke test writes PrintRxerSuiteInstaller.smoke-test.log to the extracted bundle folder where possible. The log records OK/MISS lines, PASS/FAIL, and the smoke-test exit code.

Optional HealthMailer operational validation:

$healthMailer = ".\payload\publish\HealthMailer\HealthMailer.exe"
$config = "C:\ProgramData\HealthMailer\healthmailer.settings.json"

$p = Start-Process -FilePath $healthMailer -ArgumentList @("--validate", "--config", $config) -Wait -PassThru
$p.ExitCode

$p = Start-Process -FilePath $healthMailer -ArgumentList @("--process-once", "--config", $config) -Wait -PassThru
$p.ExitCode

Diagnostics and Support

If standard troubleshooting is required, IT can compile a complete diagnostics zip archive containing registry details, local configurations, and logs.

Run the diagnostics utility script from an elevated PowerShell prompt:

& ".\payload\tools\New-PrintRxerSupportBundle.ps1"

Run this from the extracted release bundle folder.

Alternatively, open the suite launcher GUI, select Advanced / repair, and click Create support bundle.

Uninstall

Standard uninstall preserves local data, logs, and archives by default.

If printRxer printer capture is installed, run printRxer uninstall or lab reset from an administrator PowerShell session so Windows can remove printer, driver, port, and ProgramData components. Exit code 3 means insufficient permissions. 

$p = Start-Process -FilePath .\payload\setup\printRxerSetup.exe -ArgumentList @("--uninstall", "--quiet") -Wait -PassThru
$p.ExitCode

$p = Start-Process -FilePath .\payload\setup\HealthMailerSetup.exe -ArgumentList @("--uninstall", "--quiet") -Wait -PassThru
$p.ExitCode

Clean lab reset removes local data and should be used only when explicitly approved.

$p = Start-Process -FilePath .\payload\setup\printRxerSetup.exe -ArgumentList @("--uninstall", "--quiet", "--remove-data") -Wait -PassThru
$p.ExitCode

$p = Start-Process -FilePath .\payload\setup\HealthMailerSetup.exe -ArgumentList @("--uninstall", "--quiet", "--remove-data") -Wait -PassThru
$p.ExitCode

Logs

Installer logs are written to:

C:\ProgramData\printRxer\logs\printRxerInstaller.log
C:\ProgramData\HealthMailer\logs\HealthMailerInstaller.log

Runtime logs should also be reviewed under the relevant ProgramData application log folders.

Operational Safety Controls

  • READY prevents half-written package processing.
  • SHA256 validation prevents mismatched PDF and metadata sends.
  • The duplicate ledger prevents repeat sends.
  • Failed and quarantined packages are retained for review.
  • printRxer creates packages only; HealthMailer owns delivery through local Outlook.

Evidence to Retain

  • Release bundle filename and version.
  • Suite smoke-test result.
  • Component validation results.
  • Installer logs.
  • Any test package result.json and summary.txt files.

Summary

printRxer captures print jobs, prepares validated handoff packages, and writes those packages to the configured handoff folder. HealthMailer validates ready packages, sends through local Outlook/Healthmail, and archives the result for review.
